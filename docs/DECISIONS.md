# Decisions

The engineering *why*, when it is too long to live in a comment and is not a
domain rule. Domain rules — what a deal score means, what "usual" is, which
number gates an alert — stay in `docs/BUSINESS-LOGIC.md`, numbered, with their
config key beside them; this file is about how the repository is built and
checked. A short inline pointer (`See docs/DECISIONS.md: <title>`) marks the
places where "simplifying" the code would break something real.

### the-fleet-standard-is-vendored-and-drift-tested
`docs/STANDARDS.md` is a byte-identical copy of `ENGINEERING-STANDARDS.md` from the fleet's `engineering-standards` repository — not a link to it and not a summary of it. A copy is what a reviewer on GitHub, a laptop checkout and a worker in a scratch clone can all read; the canonical clone at `/srv/engineering-standards/` exists on one machine, and a rule nobody can see in the diff is a rule that gets argued about instead of followed. `.claude/rules/standards.md` is a SYMLINK to that same file rather than a second copy, so a session loads the standard at launch — no `paths:` frontmatter, which would make it load lazily, only once somebody happened to open a matching file — while there is still exactly one set of bytes in the repository to hash. Cross-repo `@path` imports would have avoided the copy altogether and were rejected: an import pointing outside the project raises a one-time approval dialog, and these sessions run unattended, so it would sit on a prompt nobody is there to answer.

The first line of the vendored file declares the version and the sha256 of every byte after it, and `tests/Unit/Standards/StandardsDriftTest` recomputes that hash. Editing the vendored text locally therefore turns the gate red, which is the whole point: the standard is amended upstream and re-vendored whole, never patched in one project. It extends `PHPUnit\Framework\TestCase` rather than `Tests\TestCase` because it only reads two files off disk and must keep working in a checkout where nothing boots — the same reason the domain tests do. A project that genuinely cannot meet a rule writes the exception into its own `CLAUDE.md` — project precedence means a local rule legitimately overrides the fleet floor, and saying so is what stops the copies quietly disagreeing. When the canonical file moves nothing here notices by itself, and nothing should: the always-on session compares each project's declared version and sha256 against the canonical repository and opens the bump PR, which arrives as an ordinary reviewable diff of the standard's own text.

### the-gate-checks-dependency-advisories
`composer audit --locked --no-dev --abandoned=report` and `npm audit --omit=dev --audit-level=high` are the gate's advisory checks, and they run in two different places on purpose. The composer half sits directly after Pint: `--locked` reads the lock file rather than the installed tree, so it really is seconds of parsing plus one advisory lookup and belongs among the cheap checks. The npm half sits immediately before ESLint instead, because it is the first step that needs `node_modules` — putting it beside the composer half would let a cold `npm ci` land minutes of install ahead of PHPStan, which is precisely the ordering the gate's own header exists to protect.

Both are scoped to what production actually installs. `--no-dev` and `--omit=dev` keep phpunit, pint, larastan, vitest and Playwright out of the result: an advisory against a package no user can be reached through would redden the gate for something unfixable-by-design and teach people to skip the step.

THE TWO SEVERITY DIALS ARE NOT THE SAME, and the difference is narrower than it looks. npm takes a floor: `--audit-level=high` passes anything below High. Composer has no floor — `composer audit --help` offers `--ignore-severity`, which is an ignore-LIST of named levels, not a minimum — so short of enumerating every severity we do not care about, it fails on any advisory it finds against a production package. We leave it there deliberately: it is stricter than the fleet bar rather than looser, and Orbit's production `require` block is short enough that the noise is affordable. If that stops being true, the honest change is an explicit `--ignore-severity` line with a reason beside it, never dropping the step.

These are also the gate steps that need the network on a warm checkout — on a cold one the guarded `npm ci` beside them needs the registry too — so a Packagist or npm outage can hold up a merge. That is the accepted cost of not learning about a known vulnerability from somewhere other than the gate.

`--abandoned=report` is deliberate: composer 2.9+ fails the audit by default when a production package is merely marked abandoned on Packagist. Abandonment is not a vulnerability and is rarely fixable the same afternoon, so the gate reports it and moves on — the stricter default was declined on purpose, not overlooked.

### the-gate-is-written-twice-and-that-is-a-debt
`scripts/check.sh` drives the *running* `app` container with `docker compose exec`, and on this box that container's `vendor/` was installed `--no-dev`: there is no Pint, no PHPStan and no phpunit in it, and installing them would install them into production, because the checkout is bind-mounted. So the deploy runbook does not call the gate script — it restates the same seven steps against a throwaway container with an overlaid `vendor/` and `bootstrap/cache`. The reason is real and the workaround is correct; the duplication is still a duplication, and this PR had to edit both to add two steps, which is exactly how the two copies drift.

Collapsing them means parameterising the runner — one script that either `exec`s into a live container or `run`s a throwaway one with the overlay — and it is a change to the gate itself, so it does not belong in the PR that vendors the standard. The follow-up branch is `chore/one-gate-two-runners`. Until it lands, a step added to one copy is added to the other in the same commit.

### the-screen-shell-is-global
`.screen`, `.screen__master`, `.screen__pane`, `.screen__head`, `.screen__notice`, `.screen__state`, `.screen__retry` and the whole `.screen--wide` master/pane frame live in `resources/css/app.css`, not in the four screens that draw them. Before this the frame lived as four copies — identical but for the watch list's pane padding — and the notice/state/retry trio was duplicated across three files (Alerts, Watchlist, DealRules; Create and Search never had it) — `Views/Alerts.vue`, `Views/Create.vue`, `Views/Search.vue`, `Views/Watchlist.vue` — plus a fifth partial copy in `Components/rules/DealRules.vue`, whose own comment said it copied them "rather than inherited" because scoped styles do not cross a component boundary. That reason was correct and the copies still drifted: `.screen__state` had picked up `padding: 0 4px` in `DealRules` and `Watchlist` and not in `Alerts`. One copy in a global sheet is what a child component can actually inherit, and it is the only arrangement in which the drift cannot come back.

THE BASE RULES HAD TO MOVE WITH THE WIDE ONES, and this is the part that is not obvious. Vue scopes a style by appending `[data-v-…]` to the selector's **last** compound — `.screen` becomes `.screen[data-v-x]` (0,2,0) and `.screen--wide .screen__pane` becomes `.screen--wide .screen__pane[data-v-x]` (0,3,0). Inside one file that ordering is what made the frame work. Hoist only the wide half and the free attribute changes sides: global `.screen--wide` is (0,1,0) and loses outright to a scoped `.screen[data-v-x]`, and global `.screen--wide .screen__master` is (0,2,0) and merely *ties* with a scoped `.screen__master[data-v-x]`. Ties are decided by document order, and Vite emits each view's styles as its own lazily-loaded chunk (`assets/Alerts-*.css`) that the browser appends **after** the entry sheet — so every tie would have gone to the scoped rule, and the wide frame would have silently rendered as the phone column. Moving `.screen`, the `display: contents` pair and `.screen__head` into the same file as the frame puts both halves back in one specificity regime: base at (0,1,0), frame at (0,2,0), and the one deliberate divergence — the watch list's tighter pane padding — kept scoped at (0,3,0), where it still wins. A screen's own content keeps its `<style scoped>` block; only the shell is global.

The proof is the browser gate, not the reading above: all 51 committed baselines — 19 at the phone's 390x844 (nine screens in both themes, plus the themeless offline page) and 32 wide (eight screens in both themes at the tablet's 820x1180 and the desktop's 1280x832), every one at `maxDiffPixels: 0` — were required to be byte-identical, and the follow-up worth having is `.screen__title` and `.screen__note`, which are also four identical copies and were left alone because nothing in the frame overrides them.

### the-travelpayouts-adapters-share-one-envelope
Three adapters talk to Travelpayouts — the calendar's `/v2/prices/month-matrix`, the return-trip and the origin-sweep readings of `/v2/prices/latest` — and until this change each one carried its own copy of the same request (base URL, the two timeouts, the `retries + 1` attempt count, the token header, `Accept-Encoding`, `acceptJson`, `show_to_affiliates=false`) and its own copy of the same four guards on the answer. The copies had already drifted where it mattered least visibly: `found_at`. The two `/v2/prices/latest` adapters accepted both UTC notations the API sends, `2026-08-14T13:51:45Z` and `2026-08-14T13:51:45`; the calendar adapter accepted only the suffixed one. Nothing was broken, because month-matrix happens to send the `Z` — but an endpoint that changed its mind would have taken the age off every calendar fare and no gate would have gone red, since a fare with an unknown age is a valid fare that alerts treat as fresh (§10).

`App\Infrastructure\Concerns\TravelpayoutsEnvelope` is that request and those guards, written once, with `App\Infrastructure\Concerns\WarnsOnce` underneath it holding the once-every-`warn_every_minutes` log line. Traits rather than a collaborator object, deliberately: this is live fare I/O, and a trait leaves all three constructor signatures, all three container factories and every test's `provider()` helper byte-identical, so the diff that has to be proven behaviour-preserving is confined to the adapters themselves. A `TravelpayoutsApi` object would have been the textbook shape and would have rewritten three constructors and three bindings to buy nothing the trait does not already buy.

What stays with each adapter is what genuinely differs: the path, the query it builds, the context every warning carries, the four sentences it logs, and its own warning key — the keys are separate on purpose, so the 05:20 sweep failing cannot silence the 06:10 and 06:40 polls. `WarnsOnce` demands that key through an abstract private method rather than reading a constant off the using class, so a new adapter that forgets it fails to compile instead of failing at 06:10.

### the-toolchain-pins-quote-the-container
Four pins, and every one names something a container already is rather than something a host happens to have. `.nvmrc` reads `24` because `docker-compose.yml`'s `assets` service is `node:24-alpine`; `package.json`'s `engines.node` reads `24.x` because `.nvmrc` reads `24`; `composer.json`'s `config.platform.php` reads `8.5.0` because `docker/app/Dockerfile` builds `FROM php:8.5-fpm-alpine` — the PHP tag lives there and not in the compose file, which only names the image that build produces (`orbit/app:latest`); and the Playwright driver in `package.json` and the browser image in `scripts/e2e.sh` are one string typed twice because Playwright refuses to drive browsers it did not ship with, so a one-character drift stops the browser gate before a single test runs. `tests/Unit/Standards/ToolchainPinsTest` reads those six files as text and goes red the moment any pair stops agreeing.

THE HOST IS NOT AN ANCHOR, and that is the whole reason these assertions compare files instead of asking a binary. This box's PHP and node are whatever the distribution installed, at versions nothing here controls, and `scripts/check.sh`'s own header says why that cannot be trusted: a gate green against a runtime production does not have is worse than no gate. A pin read off the host would describe the machine that happened to run the command. Reading the image tag instead means the pin describes the thing that actually serves the site — and the test stays a file comparison with no network and no container, so it keeps working in a checkout where nothing boots, for the same reason `StandardsDriftTest` does.

THE VALUES ARE DELIBERATELY NOT PATCH VERSIONS. On the day this landed the assets image was node 24.19.0 and the app image PHP 8.5.9, and neither number appears anywhere in the repository: both tags float within their line, so tomorrow's rebuild is 24.20.0 and 8.5.10 and a `.nvmrc` claiming `24.19.0` would be a lie with nothing able to notice it had become one. `.nvmrc` therefore carries exactly the tag — `24` — and `config.platform.php` carries `8.5.0`, the lowest PHP the `php:8.5` tag can ever contain. Composer resolves for that floor, so every 8.5.x the image might ship satisfies what was resolved; pinning it to `8.5.9` would have resolved packages against a PHP that an 8.5.0-to-8.5.8 image could not run.

WHAT THE LOCK FILE GAINED, AND WHAT IT MUST NOT. `composer update --lock` wrote exactly two things: a new content hash — composer's hash covers `config`, so the lock was genuinely stale the moment the platform key existed — and a `platform-overrides` block holding `8.5.0`. All 121 locked packages kept their version and their dist reference, checked by diffing the name/version/reference list either side of the run. That is the invariant for any future move of this pin: the platform key changes what composer resolves *for*, not what is already resolved, and a package that moves in that diff means the pin is wrong rather than that the lock was out of date.
### the-local-pre-commit-guard-has-to-be-a-superset-of-the-global-one
This box already guards every commit: `git config --global core.hooksPath` points at `/root/.githooks`, whose `pre-commit` runs gitleaks over the staged diff and then searches it for the repository's own `.env` values. Its header states the contract plainly — a repository that sets a **local** `core.hooksPath` overrides that file *entirely*, because that is git's precedence, and such a hook "is expected to be a superset of this one". So the only question worth asking about a hook in this repository is not whether it catches things; it is whether installing it can ever leave a commit less guarded than not installing it. The first draft of this one failed that test in six measured ways, and the design below exists to pass it.

Layer one is gitleaks itself — `gitleaks git --staged --redact -v` whenever it is on PATH — rather than a private imitation of it. The `-v` is load-bearing and is the one place this improves on the global hook: without it gitleaks 8.30.1 prints a banner and `leaks found: 1` and nothing else, so the global hook's `grep` for `RuleID:`/`File:` matches nothing and it blocks with an empty explanation. With `-v` the finding block appears and `--redact` masks the value inside it; this hook prints only the lines that *begin* `RuleID:`, `File:` or `Line:`, and never `Finding:` or `Secret:`. The anchor is the whole point, and it was missing at first: gitleaks' `Finding:` line quotes the offending source text, so an unanchored match let a staged line that itself contained the characters `File:` print itself straight back out. Redaction still held — the secret stayed `REDACTED`, and a second secret on the same line could not be made to ride along — but the guard was echoing source context, which is not what it promises. Nine patterns then run *in addition*, always, not merely as a fallback. They overlap gitleaks rather than replace it, and the overlap is not waste. gitleaks 8.30.1 ships rules for both Anthropic and OpenAI, but they match a *well-formed* key structurally rather than by prefix: `anthropic-api-key` keys on the trailing `AA`, so the identical key ending `ZZ` passes it untouched — measured, not assumed. The two prefix-only rules here cover what structure-matching cannot: a key that is truncated, mistyped, partially redacted, or issued in a format gitleaks has not learned yet. The remaining seven are what a machine *without* gitleaks falls back to, and that fallback is strictly better than the global hook, which skips its pattern layer entirely and says so.

Layer two is this repository's own `.env`, and it is resolved through `git rev-parse --git-common-dir`, not through `--show-toplevel`. In a linked worktree those are different places: the worktree has no `.env` of its own, because `.env` is gitignored and lives in the main checkout. The fleet commits from worktrees almost exclusively, so a hook that reads `<toplevel>/.env` has switched its most valuable layer off exactly where it is used — a real staged secret was committed cleanly through the earlier draft in a linked worktree while the hook it replaces blocked it. Key names are matched by suffix *and* by substring, so `DB_PASS`, `*_SIGNATURE` and `*_DSN` are covered alongside the obvious ones, and a DSN-shaped value is decomposed so the embedded password is searched for on its own — a connection string leaks by its password, not by the whole URL. Values are compared in-process with bash's `==` rather than handed to `grep` on a command line, where they would sit in `ps` output. One gap is deliberate: bare `KEY` is not in the substring alternation, because `*KEY*` also matches `MONKEY`, `KEYCLOAK_URL` and `KEY_ID`, and a guard that fires on those is a guard people uninstall. The price is that a name like `KEY_MATERIAL` — no `_KEY` suffix and no other secret word in it — is guarded by neither this hook nor the global one.

**IT REFUSES RATHER THAN WARNING, WHENEVER IT CANNOT FINISH THE JOB.** No readable `.env`, a missing `awk`, a bash older than 4 — each of these ends the commit, because a warning printed inside a *successful* commit scrolls past and is never read. The earlier draft warned in all three cases and exited 0; with `awk` off PATH and an AWS key staged it printed `command not found` and allowed the commit. The report itself is unchanged and is the point of the whole thing: the key and the file, `TRAVELPAYOUTS_TOKEN found in config/orbit.php`, and never the value.

Installing it is `scripts/install-hooks.sh`, which **refuses to run from a linked worktree**. `core.hooksPath` is shared configuration: setting it from a worktree arms the main checkout, which on this box is production. The honest costs are stated in `docs/DEVELOPMENT.md` rather than hidden: a checkout with no `.env` cannot commit until it has one, and `git commit --no-verify` bypasses the hook exactly as it bypasses the global one. What a clone that never installs it gets is not "no guard" — it is the global guard, which is weaker than this one but far from nothing, and that is why the follow-up branch `chore/gate-secrets-scan` matters: this repository has no CI configuration at all, so a gate step is run by a person and enforced by review, not by a mechanism that cannot be skipped.
