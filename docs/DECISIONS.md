# Decisions

The engineering *why*, when it is too long to live in a comment and is not a
domain rule. Domain rules — what a deal score means, what "usual" is, which
number gates an alert — stay in `docs/BUSINESS-LOGIC.md`, numbered, with their
config key beside them; this file is about how the repository is built and
checked. A short inline pointer (`See docs/DECISIONS.md: <title>`) marks the
places where "simplifying" the code would break something real.

### the-fleet-standard-is-vendored-and-drift-tested
`docs/STANDARDS.md` is a byte-identical copy of `ENGINEERING-STANDARDS.md` from the fleet's `engineering-standards` repository — not a link to it and not a summary of it. A copy is what a reviewer on GitHub, a laptop checkout and a worker in a scratch clone can all read; the canonical clone at `/srv/engineering-standards/` exists on one machine, and a rule nobody can see in the diff is a rule that gets argued about instead of followed. `.claude/rules/standards.md` is a SYMLINK to that same file rather than a second copy, so a session loads the standard at launch — no `paths:` frontmatter, which would make it load lazily, only once somebody happened to open a matching file — while there is still exactly one set of bytes in the repository to hash. Cross-repo `@path` imports would have avoided the copy altogether and were rejected: an import pointing outside the project raises a one-time approval dialog, and these sessions run unattended, so it would sit on a prompt nobody is there to answer.

The first line of the vendored file declares the version and the sha256 of every byte after it, and `tests/Unit/Standards/StandardsDriftTest` recomputes that hash. Editing the vendored text locally therefore turns the gate red, which is the whole point: the standard is amended upstream and re-vendored whole, never patched in one project. It extends `PHPUnit\Framework\TestCase` rather than `Tests\TestCase` because it only reads two files off disk and must keep working in a checkout where nothing boots — the same reason the domain tests do. A project that genuinely cannot meet a rule writes the exception into its own `CLAUDE.md` — project precedence means a local rule legitimately overrides the fleet floor, and saying so is what stops the copies quietly disagreeing. When the canonical file moves nothing here notices by itself, and nothing should: the always-on session compares each project's declared version and sha256 against the canonical repository and opens the bump PR, which arrives as an ordinary reviewable diff of the standard's own text.

### the-gate-checks-dependency-advisories
`composer audit --locked --no-dev --abandoned=report` and `npm audit --omit=dev --audit-level=high` are the gate's advisory checks, and they run in two different places on purpose. The composer half sits directly after Pint: `--locked` reads the lock file rather than the installed tree, so it really is seconds of parsing plus one advisory lookup and belongs among the cheap checks. The npm half sits immediately before ESLint instead, because it is the first step that needs `node_modules` — putting it beside the composer half would let a cold `npm ci` land minutes of install ahead of PHPStan, which is precisely the ordering the gate's own header exists to protect.

Both are scoped to what production actually installs. `--no-dev` and `--omit=dev` keep phpunit, pint, larastan, vitest and Playwright out of the result: an advisory against a package no user can be reached through would redden the gate for something unfixable-by-design and teach people to skip the step.

THE TWO SEVERITY DIALS ARE NOT THE SAME, and the difference is narrower than it looks. npm takes a floor: `--audit-level=high` passes anything below High. Composer has no floor — `composer audit --help` offers `--ignore-severity`, which is an ignore-LIST of named levels, not a minimum — so short of enumerating every severity we do not care about, it fails on any advisory it finds against a production package. We leave it there deliberately: it is stricter than the fleet bar rather than looser, and Orbit's production `require` block is short enough that the noise is affordable. If that stops being true, the honest change is an explicit `--ignore-severity` line with a reason beside it, never dropping the step.

These are also the gate steps that need the network on a warm checkout — on a cold one the guarded `npm ci` beside them needs the registry too — so a Packagist or npm outage can hold up a merge. That is the accepted cost of not learning about a known vulnerability from somewhere other than the gate.

`--abandoned=report` is deliberate: composer 2.9+ fails the audit by default when a production package is merely marked abandoned on Packagist. Abandonment is not a vulnerability and is rarely fixable the same afternoon, so the gate reports it and moves on — the stricter default was declined on purpose, not overlooked.

### the-gate-scans-for-secrets-over-gits-view-of-the-tree
Gitleaks runs first in the gate, in a container pinned to `zricethezav/gitleaks:v8.30.1` — the tag, never `latest`. A scanner is a rule set, so `latest` means the gate's verdict can change overnight without a commit: a rule added upstream reddens a branch nobody touched, a rule dropped upstream stops catching what it caught yesterday, and "green on this commit" stops meaning anything tomorrow. There is no host binary either: a scanner installed by whoever happened to have one is the tool where a version difference is silently a coverage difference.

WHAT IS SCANNED IS THE POINT, AND IT IS NOT THE FILESYSTEM. The step asks git for the files git itself would consider — `git ls-files --cached --others --exclude-standard`, everything tracked plus everything untracked that is not ignored — copies exactly those into a throwaway directory, and mounts *that* directory read-only into the container. Nothing else is ever visible to the scanner. Pointing gitleaks at the checkout instead would have been shorter and would have read `.env`: a real one, with live tokens and the app key, sits in `/var/www/orbit`, which is precisely where the deploy runbook's copy of this gate runs. That gate would have gone red on the first deploy after this landed, would have stayed red, and its output would have been the production secrets — the one failure mode a secrets scanner must not have. Copying git's own list makes that structurally impossible rather than one flag away: the file is not on the mount. Symlinks are left unfollowed for the same reason — `tar` copies the link and not its target, and `--follow-symlinks` is not passed.

The untracked-but-not-ignored half is deliberate, and it is where the step earns its place: a key pasted into a new file is caught before it is ever committed, which is the only moment it can still be taken back. History is not a gate step, because a branch's verdict must depend on the branch and not on how many commits sit behind it. It was scanned once, whole — every ref, 230 commits, 7.45 MB — and is clean, so there is nothing to rewrite and nothing to hide: there is no `.gitleaks.toml`, and `.env.example`'s placeholders and the committed `.env.testing` pass the default rule set as they stand. Re-checking history is a one-off run, not a step.

`--redact` is not optional: a gate that prints what it caught has just copied the secret into a terminal, a scrollback and a log, so the finding names the rule, the file and the line and nothing else. `--verbose` is what prints those findings at all — without it the step reports only a count, which is a number you cannot act on. The step cannot skip itself: if the image cannot be pulled, `docker run` exits non-zero and `set -euo pipefail` stops the gate there. It runs first because it is the cheapest thing in it — under a second over 3.7 MB — and because ninety seconds of static analysis on a branch that is going to be rejected for a leaked key is ninety seconds wasted. The runbook's copy sits in the same position, after the overlay's `composer install` and before Pint, for the reason the entry below gives.

AN EMPTY SCAN IS A FAILURE, NOT A PASS. The step asks git for the list, writes it to a file, and refuses to go on if that file is empty — because the shape this started as, `git ls-files … | tar | tar`, reports the exit status of the last `tar`, and `tar` succeeds on empty input. A `git` that died of a wrong working directory or of `dubious ownership` therefore produced an empty directory, a cheerful `no leaks found` and a green tick. The developer runner was accidentally safe, since `check.sh` sets `pipefail`; the copy the runbook used to carry was pasted into an operator's shell, which has neither `errexit` nor `pipefail` — and that is the one that runs as root against `/var/www/orbit`, where a real `.env` is on disk. That copy is gone (see `the-gate-is-one-script-two-runners`) and the one remaining step asserts that git listed something and that the copied directory is not empty, saying on stderr which of the two failed. It uses `git -C <explicit path>` AND `tar -C <the same path>`, never a bare one. `git -C` alone is not enough and the gap is nastier than it looks: git prints the list relative to that path, so a `tar` reading it from somewhere else fills the copy from whatever checkout the shell happened to be in. Where the two trees share no paths `tar` fails loudly; where they share them — two worktrees of one repository, which is this project's mandated layout — the step scans the wrong tree and reports a green tick for it. Note also what is NOT containerised: only the scanner is, and the step leans on the host's `git`, `tar`, `grep -z`, `mktemp` and `ls -A`. That is a stated partial exception to the rule that the gate runs in the containers, and an unavoidable one, because git's view of a tree can only come from the git that owns the tree.

THE SCANNED CODE MUST NOT GET A VOTE ON WHAT THE SCANNER FINDS. gitleaks reads `(target path)/.gitleaks.toml` when no config is named, and the target path here is a copy of the repository — so five committed lines beside a live key turn `leaks found: 1` into `no leaks found`, and `.gitleaksignore` and an inline `# gitleaks:allow` comment do the same thing without one. That is a PHPStan baseline wearing a different hat, in a repository whose rule is that there is nowhere for new debt to hide. So the step refuses to run at all when git's own list carries `.gitleaks.toml` or `.gitleaksignore` anywhere in the tree — refusing rather than quietly ignoring them, because a file that sits there looking effective is worse than no file — and passes `--ignore-gitleaks-allow` for the comment form. Neither file is tracked today: this prevents a future rather than fixes a present, and a genuinely needed allowlist would be a change to the gate itself, visible in a diff, which is the only place it belongs. `--network none` is the same instinct: a scanner reading a read-only mount has nobody to talk to.

`-c safe.directory` is deliberately NOT baked into the step. git refusing to work in a checkout its caller does not own is a security check, and hard-coding the bypass for it inside a security gate is how a control dies quietly. The step fails with git's own actionable message instead, and the assertions above are what turn that failure into a stop rather than a green tick.

### the-gate-is-one-script-two-runners
`scripts/check.sh` takes the runner as its one argument and refuses to guess one: `dev` drives the stack already up from this checkout with `docker compose exec -T app`, `overlay` gives every PHP step its own `docker compose run --rm --no-deps` container with `vendor/` and `bootstrap/cache` bind-overlaid onto directories outside the tree. The nine checks, their order, their flags and their assertions are written once; the two runners differ only in how a PHP command is delivered to a container, which is the only thing that ever differed. The node steps are identical in both, because `assets` is a profile-gated task that brings its own `node_modules` and is `--no-dev` in neither. BOTH RUNNERS RUN IN THE CONTAINERS AND NEITHER RUNS ON THE HOST: the host's PHP and node are whatever the distribution installed, at versions nothing here controls, and a gate green against a runtime production does not have is worse than no gate, because it is believed. The one stated exception is the secrets step, which leans on the host's `git`, `tar`, `grep -z` and `mktemp` for the reason the entry above it gives.

WHY TWO RUNNERS RATHER THAN ONE. The live `app` container's `vendor/` is installed `--no-dev` (deploy step 3), so it holds no Pint, no PHPStan and no phpunit, and the checkout is bind-mounted into `app`, `horizon` and `scheduler` — installing dev dependencies to make `exec` work would install them *in production*. So the deploy runbook cannot use the developer's runner, and the developer, whose stack is up with dev dependencies present, should not pay for a `composer install` per gate run. Both facts are permanent. What was not permanent was the shape: for four months the runbook restated the same steps in a fenced block of its own, under a written rule that a step added to one copy is added to the other in the same commit. That rule was obeyed twice this week and the copies still drifted in wording, which is what a rule enforced by discipline does. The runbook now calls the script and keeps what a runbook is for — the warnings, the expected output, and why the flags are what they are.

WHAT `overlay` MAY NOT LOSE, AND IT IS `bootstrap/cache` RATHER THAN `vendor`. The overlay's `composer install` fires `@php artisan package:discover`, which writes `bootstrap/cache/packages.php` and `services.php` — the provider list the framework loads at boot. With dev dependencies present that list names dev-only providers, and those files sit in the same bind-mounted checkout, so the live `--no-dev` app reads them on its next boot, cannot find the class, and answers **every request with a 500**: an outage caused by a gate run, minutes after it reported all green. Overlaying `vendor/` alone would have been the obvious half of the fix and the dangerous one. The overlay lives at a fresh `mktemp -d /var/tmp/orbit-gate.XXXXXXXX` rather than one fixed path, and the step sweeps `orbit-gate.*` before making its own: the `trap` reclaims the directory on success, on failure and on SIGINT or SIGTERM, but not on SIGKILL, and an OOM kill — this box's largest historical failure mode — would otherwise strand a full dev vendor tree per run. The sweep is what the fixed path used to give for free, and it means two overlay runs must not overlap; the gate is serialised box-wide by `heavy-work`, and the fixed path could not have overlapped either. `--no-deps` is the other keeper: `run` must not start or restart `postgres` and `redis` behind an operator's back, and the suite needs neither.

THE MODE IS AN ARGUMENT, NOT A DEFAULT, and that is deliberate. A default would be wrong for whichever caller did not type it, and the caller that would inherit it silently is the one running as root against `/var/www/orbit` with a real `.env` on disk. `scripts/check.sh` with no argument prints both runners and exits 2. `set -euo pipefail` and the cleanup `trap` now live inside a script rather than in a block an operator pastes, so neither can reach the operator's interactive shell and the overlay is removed however the run ends — the two properties the runbook's subshell existed to fake.

THE STARTED-FROM-ANOTHER-DIRECTORY GUARD NOW COVERS BOTH RUNNERS. It was written for `dev`, where gating production's containers from a worktree is the accident it prevents; `overlay` had none, and `docker compose run` resolves through the pinned `name: orbit` exactly as `exec` does, so an overlay run launched from a worktree would have built its throwaway container in production's project. Run from `/var/www/orbit`, where the deploy runs it, every `orbit` container reports `com.docker.compose.project.working_dir=/var/www/orbit` and the guard passes.

THE NODE INSTALL GUARD TESTS FOR AN INSTALL, NOT FOR A DIRECTORY. It was `[ -d node_modules ] || npm ci`, which is a test for presence: an empty `node_modules/` — left by an interrupted install, or by a `mkdir` in a Dockerfile or an ownership fix — satisfied it, `npm ci` was skipped, and the step then exited 127 having linted nothing. Two people hit that in one week. It is now `[ -f node_modules/.package-lock.json ]`, the marker npm itself writes when an install finishes, and it guards all three node steps rather than two: Vitest used to lean on ESLint having run first, which is a coupling that only holds while nobody reorders the list.

### the-screen-shell-is-global
`.screen`, `.screen__master`, `.screen__pane`, `.screen__head`, `.screen__notice`, `.screen__state`, `.screen__retry` and the whole `.screen--wide` master/pane frame live in `resources/css/app.css`, not in the four screens that draw them. Before this the frame lived as four copies — identical but for the watch list's pane padding — and the notice/state/retry trio was duplicated across three files (Alerts, Watchlist, DealRules; Create and Search never had it) — `Views/Alerts.vue`, `Views/Create.vue`, `Views/Search.vue`, `Views/Watchlist.vue` — plus a fifth partial copy in `Components/rules/DealRules.vue`, whose own comment said it copied them "rather than inherited" because scoped styles do not cross a component boundary. That reason was correct and the copies still drifted: `.screen__state` had picked up `padding: 0 4px` in `DealRules` and `Watchlist` and not in `Alerts`. One copy in a global sheet is what a child component can actually inherit, and it is the only arrangement in which the drift cannot come back.

THE BASE RULES HAD TO MOVE WITH THE WIDE ONES, and this is the part that is not obvious. Vue scopes a style by appending `[data-v-…]` to the selector's **last** compound — `.screen` becomes `.screen[data-v-x]` (0,2,0) and `.screen--wide .screen__pane` becomes `.screen--wide .screen__pane[data-v-x]` (0,3,0). Inside one file that ordering is what made the frame work. Hoist only the wide half and the free attribute changes sides: global `.screen--wide` is (0,1,0) and loses outright to a scoped `.screen[data-v-x]`, and global `.screen--wide .screen__master` is (0,2,0) and merely *ties* with a scoped `.screen__master[data-v-x]`. Ties are decided by document order, and Vite emits each view's styles as its own lazily-loaded chunk (`assets/Alerts-*.css`) that the browser appends **after** the entry sheet — so every tie would have gone to the scoped rule, and the wide frame would have silently rendered as the phone column. Moving `.screen`, the `display: contents` pair and `.screen__head` into the same file as the frame puts both halves back in one specificity regime: base at (0,1,0), frame at (0,2,0), and the one deliberate divergence — the watch list's tighter pane padding — kept scoped at (0,3,0), where it still wins. A screen's own content keeps its `<style scoped>` block; only the shell is global.

The proof is the browser gate, not the reading above: all 51 committed baselines — 19 at the phone's 390x844 (nine screens in both themes, plus the themeless offline page) and 32 wide (eight screens in both themes at the tablet's 820x1180 and the desktop's 1280x832), every one at `maxDiffPixels: 0` — were required to be byte-identical, and the follow-up worth having is `.screen__title` and `.screen__note`, which are also four identical copies and were left alone because nothing in the frame overrides them.

### the-travelpayouts-adapters-share-one-envelope
Three adapters talk to Travelpayouts — the calendar's `/v2/prices/month-matrix`, the return-trip and the origin-sweep readings of `/v2/prices/latest` — and until this change each one carried its own copy of the same request (base URL, the two timeouts, the `retries + 1` attempt count, the token header, `Accept-Encoding`, `acceptJson`, `show_to_affiliates=false`) and its own copy of the same four guards on the answer. The copies had already drifted where it mattered least visibly: `found_at`. The two `/v2/prices/latest` adapters accepted both UTC notations the API sends, `2026-08-14T13:51:45Z` and `2026-08-14T13:51:45`; the calendar adapter accepted only the suffixed one. Nothing was broken, because month-matrix happens to send the `Z` — but an endpoint that changed its mind would have taken the age off every calendar fare and no gate would have gone red, since a fare with an unknown age is a valid fare that alerts treat as fresh (§10).

`App\Infrastructure\Concerns\TravelpayoutsEnvelope` is that request and those guards, written once, with `App\Infrastructure\Concerns\WarnsOnce` underneath it holding the once-every-`warn_every_minutes` log line. Traits rather than a collaborator object, deliberately: this is live fare I/O, and a trait leaves all three constructor signatures, all three container factories and every test's `provider()` helper byte-identical, so the diff that has to be proven behaviour-preserving is confined to the adapters themselves. A `TravelpayoutsApi` object would have been the textbook shape and would have rewritten three constructors and three bindings to buy nothing the trait does not already buy.

What stays with each adapter is what genuinely differs: the path, the query it builds, the context every warning carries, the four sentences it logs, and its own warning key — the keys are separate on purpose, so the 05:20 sweep failing cannot silence the 06:10 and 06:40 polls. `WarnsOnce` demands that key through an abstract private method rather than reading a constant off the using class, so a new adapter that forgets it fails to compile instead of failing at 06:10.

### the-toolchain-pins-quote-the-container
Four pins, and every one names something a container already is rather than something a host happens to have. `.nvmrc` reads `24` because `docker-compose.yml`'s `assets` service is `node:24-alpine`; `package.json`'s `engines.node` reads `24.x` because `.nvmrc` reads `24`; `composer.json`'s `config.platform.php` reads `8.5.0` because `docker/app/Dockerfile` builds `FROM php:8.5-fpm-alpine` — the PHP tag lives there and not in the compose file, which only names the image that build produces (`orbit/app:latest`); and the Playwright driver in `package.json` and the browser image in `scripts/e2e.sh` are one string typed twice because Playwright refuses to drive browsers it did not ship with, so a one-character drift stops the browser gate before a single test runs. `tests/Unit/Standards/ToolchainPinsTest` reads those six files as text and goes red the moment any pair stops agreeing.

THE HOST IS NOT AN ANCHOR, and that is the whole reason these assertions compare files instead of asking a binary. This box's PHP and node are whatever the distribution installed, at versions nothing here controls, and the entry above (`the-gate-is-one-script-two-runners`) says why that cannot be trusted: a gate green against a runtime production does not have is worse than no gate. A pin read off the host would describe the machine that happened to run the command. Reading the image tag instead means the pin describes the thing that actually serves the site — and the test stays a file comparison with no network and no container, so it keeps working in a checkout where nothing boots, for the same reason `StandardsDriftTest` does.

THE VALUES ARE DELIBERATELY NOT PATCH VERSIONS. On the day this landed the assets image was node 24.19.0 and the app image PHP 8.5.9, and neither number appears anywhere in the repository: both tags float within their line, so tomorrow's rebuild is 24.20.0 and 8.5.10 and a `.nvmrc` claiming `24.19.0` would be a lie with nothing able to notice it had become one. `.nvmrc` therefore carries exactly the tag — `24` — and `config.platform.php` carries `8.5.0`, the lowest PHP the `php:8.5` tag can ever contain. Composer resolves for that floor, so every 8.5.x the image might ship satisfies what was resolved; pinning it to `8.5.9` would have resolved packages against a PHP that an 8.5.0-to-8.5.8 image could not run.

WHAT THE LOCK FILE GAINED, AND WHAT IT MUST NOT. `composer update --lock` wrote exactly two things: a new content hash — composer's hash covers `config`, so the lock was genuinely stale the moment the platform key existed — and a `platform-overrides` block holding `8.5.0`. All 121 locked packages kept their version and their dist reference, checked by diffing the name/version/reference list either side of the run. That is the invariant for any future move of this pin: the platform key changes what composer resolves *for*, not what is already resolved, and a package that moves in that diff means the pin is wrong rather than that the lock was out of date.
### the-local-pre-commit-guard-has-to-be-a-superset-of-the-global-one
This box already guards every commit: `git config --global core.hooksPath` points at `/root/.githooks`, whose `pre-commit` runs gitleaks over the staged diff and then searches it for the repository's own `.env` values. Its header states the contract plainly — a repository that sets a **local** `core.hooksPath` overrides that file *entirely*, because that is git's precedence, and such a hook "is expected to be a superset of this one". So the only question worth asking about a hook in this repository is not whether it catches things; it is whether installing it can ever leave a commit less guarded than not installing it. The first draft of this one failed that test in six measured ways, and the design below exists to pass it.

Layer one is gitleaks itself — `gitleaks git --staged --redact -v` whenever it is on PATH — rather than a private imitation of it. The `-v` is load-bearing and is the one place this improves on the global hook: without it gitleaks 8.30.1 prints a banner and `leaks found: 1` and nothing else, so the global hook's `grep` for `RuleID:`/`File:` matches nothing and it blocks with an empty explanation. With `-v` the finding block appears and `--redact` masks the value inside it; this hook prints only the lines that *begin* `RuleID:`, `File:` or `Line:`, and never `Finding:` or `Secret:`. The anchor is the whole point, and it was missing at first: gitleaks' `Finding:` line quotes the offending source text, so an unanchored match let a staged line that itself contained the characters `File:` print itself straight back out. Redaction still held — the secret stayed `REDACTED`, and a second secret on the same line could not be made to ride along — but the guard was echoing source context, which is not what it promises. Nine patterns then run *in addition*, always, not merely as a fallback. They overlap gitleaks rather than replace it, and the overlap is not waste. gitleaks 8.30.1 ships rules for both Anthropic and OpenAI, but they match a *well-formed* key structurally rather than by prefix: `anthropic-api-key` keys on the trailing `AA`, so the identical key ending `ZZ` passes it untouched — measured, not assumed. The two prefix-only rules here cover what structure-matching cannot: a key that is truncated, mistyped, partially redacted, or issued in a format gitleaks has not learned yet. The remaining seven are what a machine *without* gitleaks falls back to, and that fallback is strictly better than the global hook, which skips its pattern layer entirely and says so.

Layer two is this repository's own `.env`, and it is resolved through `git rev-parse --git-common-dir`, not through `--show-toplevel`. In a linked worktree those are different places: the worktree has no `.env` of its own, because `.env` is gitignored and lives in the main checkout. The fleet commits from worktrees almost exclusively, so a hook that reads `<toplevel>/.env` has switched its most valuable layer off exactly where it is used — a real staged secret was committed cleanly through the earlier draft in a linked worktree while the hook it replaces blocked it. Key names are matched by suffix *and* by substring, so `DB_PASS`, `*_SIGNATURE` and `*_DSN` are covered alongside the obvious ones, and a DSN-shaped value is decomposed so the embedded password is searched for on its own — a connection string leaks by its password, not by the whole URL. Values are compared in-process with bash's `==` rather than handed to `grep` on a command line, where they would sit in `ps` output. One gap is deliberate: bare `KEY` is not in the substring alternation, because `*KEY*` also matches `MONKEY`, `KEYCLOAK_URL` and `KEY_ID`, and a guard that fires on those is a guard people uninstall. The price is that a name like `KEY_MATERIAL` — no `_KEY` suffix and no other secret word in it — is guarded by neither this hook nor the global one.

**IT REFUSES RATHER THAN WARNING, WHENEVER IT CANNOT FINISH THE JOB.** No readable `.env`, a missing `awk`, a bash older than 4 — each of these ends the commit, because a warning printed inside a *successful* commit scrolls past and is never read. The earlier draft warned in all three cases and exited 0; with `awk` off PATH and an AWS key staged it printed `command not found` and allowed the commit. The report itself is unchanged and is the point of the whole thing: the key and the file, `TRAVELPAYOUTS_TOKEN found in config/orbit.php`, and never the value.

Installing it is `scripts/install-hooks.sh`, which **refuses to run from a linked worktree**. `core.hooksPath` is shared configuration: setting it from a worktree arms the main checkout, which on this box is production. The honest costs are stated in `docs/DEVELOPMENT.md` rather than hidden: a checkout with no `.env` cannot commit until it has one, and `git commit --no-verify` bypasses the hook exactly as it bypasses the global one. What a clone that never installs it gets is not "no guard" — it is the global guard, which is weaker than this one but far from nothing, and that is why the follow-up branch `chore/gate-secrets-scan` matters: this repository has no CI configuration at all, so a gate step is run by a person and enforced by review, not by a mechanism that cannot be skipped.

### the-create-screens-limit-is-a-sentence-not-a-truncation
`maxlength="500"` on the rule textarea was the app's only limit nobody was told about: the browser stopped accepting characters mid-word, printed nothing, announced nothing, and left a sentence that read as if the person had finished writing it. C13 names that attribute directly. The limit itself is real and stays — it is `ParseRuleRequest`'s `max:500`, and the screen now says so in the server's own words, in the paragraph under the box that already answers for a refused parse, with `aria-describedby` pointing the textarea at it. The CTA is deliberately left as it was: a button that greys out is a second thing to explain, and the sentence is the explanation.

THE SCREEN HOLDS ITS OWN COPY OF THAT SENTENCE, AND A TEST HOLDS THE COPIES TOGETHER. The obvious alternative — delete the attribute and let the 422 say it — was rejected on two counts: `POST /rules/parse` is throttled to 20 a minute (`docs/API.md`), so a doomed request spends budget the real parses need and can come back 429, answering "slow down" to a question about length; and offline the same path says "Could not reach Orbit", which is true and useless. So `Create.vue` refuses over-length text before it asks, and `tests/Unit/Standards/NativeValidationUiTest` reads both files and goes red the moment the sentence or the number stops matching the server's. The scan the test carries is wider than the attribute this branch removed — `pattern` and `type="date"` are looked for too, because a tripwire that catches only the vector already fixed lets the next one through. `required` is deliberately NOT looked for: the five that exist (`Views/Login.vue`, `Components/settings/ChangePassword.vue`) sit on forms carrying `novalidate`, which turns constraint validation off, so they raise no bubble and enforce nothing — and the attribute is what maps to `aria-required` for assistive technology, so stripping it without putting that back would cost accessibility to satisfy the letter of a rule that exists for it. This is one field's copy, not the shared rules module C12 wants: that module lives in `resources/js/lib/`, covers all three forms, and is still `feat/inline-validation`'s to build — nothing here meets that exception's drop condition, and it stays in `CLAUDE.md`.

### the-stagger-buys-the-headroom-and-a-guard-keeps-it
Travelpayouts allows ~200 requests an hour per IP. At three minutes' stagger all thirteen watched routes' polls landed inside the 06:00 clock hour, so that hour cost 7 × 13 + the rule sweep's 120 = **211**. `docs/BUSINESS-LOGIC.md` had predicted the breach at twelve routes and named the remedy — "a wider stagger or moving the sweep" — and the app crossed the line without anything noticing.

WHY SIX MINUTES AND NOT FIVE. A wider stagger pushes a fan-out's tail into the next clock hour, where the headroom is; the smallest value that fixes the 06:00 hour is five (190). Six was chosen instead for three reasons. First, a per-IP allowance is at least as likely to be a rolling sixty-minute window as a clock hour, and the two answers differ: over any sixty minutes, five still peaks at **204** — over the limit — while six peaks at 190 and clock-hour peaks at 183. Second, at five the eleventh route (index 10) is dispatched at exactly 07:00:00, which is a knife-edge place to put a job whose whole purpose is to be in the later hour. Third — and this is the argument that closes it — **seven is already too wide**: at thirteen routes the last poll is dispatched 07:34 and needs until 07:38, past `orbit:alerts` at 07:35, so seven breaches alert clearance today. Six is the only value that satisfies both limits at the watchlist as it stands. It leaves seventeen requests of clock-hour headroom, holds to eighteen watched routes on the request budget, and restores the 183 the documents already treat as the ordinary morning. Seven and above are cheaper still per hour but breach *earlier* as the watchlist grows — past about seven minutes the far poll's tail reaches the 06:00 hour and joins the sweep there — so wider is not monotonically safer, which is exactly why this is computed rather than reasoned about.

WHAT IT COSTS, STATED RATHER THAN DISCOVERED LATER. The fan-out now runs seventy-two minutes instead of thirty-six. Two things that used to be true no longer are: the 06:40 rule sweep has five routes away and a sixth going out as it starts, leaving seven still queued where three minutes left two, so it can spend part of its cap re-fetching routes the poll is about to fetch anyway (a waste inside a fixed budget, not an overspend); and `orbit:alerts` at 06:55 would no longer have seen the whole morning — the last five of thirteen routes are polled after it. Rather than accept a day's delay on those five, the alert run moved with the stagger. Do not tidy it back to 06:55.

THE GUARD READS THE WORLD, NOT A DOCUMENT. `App\Application\Pricing\FareRequestBudget` counts `Route::onWatchlist()` and the active deal rules, builds the hour-by-hour table out of `orbit.poll.stagger_minutes`, `orbit.rules.sweep_cap`, `orbit.origins` and `orbit.discovery.shortlist`, and logs at `ERROR` when the busiest **clock hour or any sixty minutes** crosses `orbit.travelpayouts.hourly_request_limit`. Both readings are checked because the entry above rejects a five-minute stagger on the rolling one: a guard blind to it would have answered all-clear to the very configuration this file documents as over the limit, while its own remedy sentence told the reader to widen the stagger. That is one of the two limits it watches; the other is below. Two things it deliberately does not do: it does not take the watchlist size as a parameter from a caller, and it does not carry its own copy of the schedule's clock — `tests/Feature/ScheduleTest` compares its five times against the events `routes/console.php` actually registers, and `tests/Unit/Infrastructure/TravelpayoutsPriceProviderTest` bills each configured window against the recorded API and asserts the result equals the per-route costs this class assumes. Active *rules* are counted because `sweep_cap` is per rule (§34): a second active rule puts another 120 in the 06:00 hour on its own, and that is the other way this breaches. `rollingPeak(60)` can never be *below* `peak()` — every clock hour's jobs lie inside the sixty minutes that start at that hour's first job — so `exceeds()`'s `max(...)` is a defensive reading of one measure rather than two independent ones, and the clock-hour wording is reached only on an exact tie; keep both numbers anyway, because the message quotes whichever one it names.

WHERE IT IS LOUD. It runs inside `orbit:poll-fares`, which the scheduler container runs every morning at 06:10, and again on every `POST /api/watchlist` — so the route that crosses the line says so as it is added rather than at the next morning's poll. The sentence goes to the log at `production.ERROR` and to the command's own output, which means it appears in `docker compose logs scheduler`, in `storage/logs/laravel.log`, and in the deploy runbook's post-deploy check 8, which already greps that file for `production.ERROR`. It does not mail anybody and does not fail the poll: the requests still have to be made, and a run that refuses to poll is a worse outcome than a run that is over budget.

WHY THE ALERT RUN IS AT 07:35 AND NOT A ROUNDER NUMBER. The last route is dispatched at 06:10 + 12 × 6 = **07:22**, and the scheduler fires within its minute, so call it 07:22:59. One `PollRoutePrices` is up to seven provider calls, each a 15s timeout plus one retry after 500ms — 7 × 30.5s = **3m34s** worst case. Picked up immediately that finishes at 07:26:33; behind one other poll job of the same length, 07:30:07. **07:30 is therefore the worst case itself, not the safe side of it** — the same knife-edge that ruled out a five-minute stagger, and the failure here is silent: a route polled one second late is simply not in that morning's alert. 07:35 clears it by five minutes.

The ceiling is 08:00, and it is not a preference. Quiet hours default to 22:00-08:00 and are on by default, so both 06:55 and 07:35 are *inside* the window: the deal is written to the ledger at evaluation time and the mail is queued for 08:00 (§10). Moving the run to 08:00 or later would take it outside the window, and the mail would start going out at evaluation time instead of being held — a change to when people are interrupted, which nobody asked for. So the run has to live in (07:30, 08:00), and 07:35 is the earliest minute safely inside it.

THE SECOND LIMIT, WHICH BINDS FIRST. 07:35 clears the fan-out to **fourteen** watched routes, not the fifteen a dispatch-only reading suggests: the last poll is dispatched at 06:10 + 6(W-1) and then has to run. `FareRequestBudget::pollCompletionMinutes()` derives that from the adapter's own config — seven near months × (`retries` + 1) × `timeout` plus the retry delays, 3m34s, rounded up to four minutes — so raising a timeout tightens the rule automatically rather than silently invalidating it. W = 14 finishes 07:32 and clears; W = 15 is dispatched 07:34, finishes 07:38, and does not. **At today's thirteen that is one route of headroom, against five for the request budget**, so this is the limit that binds and the one Ghie will meet first. `warnAboutBreaches()` therefore returns a list rather than one sentence: the two problems have opposite fixes, and the message says so — widening `stagger_minutes` is the cure for the first and the cause of the second. A reader must not have to work out which one they have, so each sentence names its limit and each log line carries `limit: provider_hourly_requests` or `limit: alert_run_clearance`. Both run from `orbit:poll-fares` — ahead of its empty-watchlist return, since nought routes and two active rules is still 240 in the 06:00 hour — and from every write that moves either input: adding a route, pausing or resuming one, writing a rule, pausing or resuming one.

WHAT NEITHER LIMIT MODELS, AND IT IS THE LIKELIER FAILURE. `config/horizon.php` sets `tries => 1` and `timeout => 60`, so a poll job is **killed at sixty seconds** and never retried: the 3m34s worst case the clearance rule is built on cannot actually happen, and the rule is conservative by roughly one route — the safe direction, and left as it is because the adapter's own timeouts are the honest upper bound to quote. But the real way a route goes missing from a morning's alert is that its job was *killed*, not that it was still queued, and nothing here notices that: `FareRequestBudget` reads the schedule, not the queue. A `failed_jobs` row is the only trace. Watching Horizon's failures is the next thing this guard is missing, and it is deliberately not in this change. Concurrency is not a factor: `maxProcesses: 10` on the one queue means the sweep's thirty jobs at 06:40 do not push the poll's tail behind them.

WHY THE OLD TEST COULD NOT HAVE CAUGHT THIS. `TravelpayoutsPriceProviderTest::the_two_mornings_both_fit_inside_the_providers_hourly_limit` opened `$watched = 9`, computed `9 × 7 + 120`, and asserted the answer was 183. Both sides came from the same three literals, so it was green every day the app was over the limit and could not have gone red for any watchlist. Its scaling assertions were the valuable half and are kept, reframed: they now describe the *burst* — no stagger, twelve routes, 204 — which is what the stagger exists to prevent, and they are built from the config the app reads rather than retyped. The far run's old "room to sixteen" was measured on its own; counted with the returns poll that shares its hour, an unstaggered far morning breaches AT sixteen rather than having room to it, which is one more reason the arithmetic belongs in a thing that adds up hours rather than in a sentence.

### the-layer-rule-is-executed-not-reviewed
`docs/PLAN.md` has described three layers since PR1 and `CLAUDE.md` repeated them, but nothing ran: the rule was review-only, and review is what a rule falls back to when the tool is missing. `deptrac.yaml` now states it and `scripts/check.sh` runs it between `composer audit` and PHPStan — deptrac parses sources where PHPStan boots the framework through Larastan at 512M, so cheapest-first puts it ahead while keeping the PHP-analysis steps together.

EIGHT LAYERS, BECAUSE THREE DO NOT COVER `app/`. `Domain`, `Application` and `Infrastructure` are the ones the plan names. `Eloquent` is `app/Models`, separate because "Eloquent used directly for plain CRUD — no repository ceremony" is a deliberate local rule and a layer is where it gets written down: Application and Infrastructure may reach a model, Domain may not. `SyncDispatch` and `Queue` split `app/Jobs` (below); `Edge` is `app/Console`, `app/Http`, `app/Providers` and `app/Services`. Everything in `app/` sits in exactly one layer on purpose — a class in none is invisible to the tool, and Domain importing a controller would then be reported as nothing at all. `Vendor` is everything Composer installed, collected as "class name not starting with `App\`" **minus** `php_internal`, and that subtraction is the whole trick: with `Domain: ~` allowing nothing, a single `use Illuminate\…` in `app/Domain` is a violation, while `DateTimeImmutable` and `InvalidArgumentException` stay legal. That is "pure PHP, imports no framework" as something a machine reads rather than something a reviewer remembers. Enumerating vendor namespaces was rejected: a namespace nobody added to the list is a framework import Domain gets away with.

`app/Notifications` IS INFRASTRUCTURE, NOT THE EDGE. Its only importer is `App\Infrastructure\Notify\MailDealNotifier`, the `DealNotifier` adapter; a Laravel `Notification` here is the mail channel's payload, not an entry point. Filed at the edge it produced four violations that described the classification rather than the code, which is what a wrong finding looks like. The correction is also net-tightening rather than net-loosening: `Notifications → Queue` was legal under the Edge filing and is a violation now, while Domain and Application could not reach it either way.

WHAT TURNING IT ON COST. `App\Application\Routes\LivePriceChecks` took `App\Infrastructure\Verify\GoogleFlightsCheck` in its constructor — a use case holding an adapter, the exact direction the rule exists to forbid. It now takes `App\Application\Ports\LiveFareCheck`, which `GoogleFlightsCheck` implements and `AppServiceProvider` binds. The port carries two of the adapter's six public methods, which is the two the use case calls, and the other callers keep the concrete class for reasons the port cannot serve: `DiscoverDeals` uses `check()`, the nullable-verdict variant deliberately left off the port, and `SettingsController` reads `isConfigured()`, `reserve()` and `searchesLeft()`, which are the adapter's own quota rather than a use case's.

DEPTRAC CHECKS EDGES, NOT PATHS, AND THAT IS WHY `app/Jobs` IS TWO LAYERS. `FareFreshness::refreshIfStale()` runs `PollRoutePrices` and `RefreshRouteStats` with `dispatchSync`, so a lookup prices the route inside the request; that dependency has to be legal or the fix is a refactor of ten call sites and a decision about what `app/Jobs` *is*, which the plan has never made. Allowing `Application → Queue` wholesale was the first shape and it was wrong: `DiscoverDeals` holds `GoogleFlightsCheck`, so a use case could reach an adapter in two legal hops — write the work into a job, `dispatchSync` it, green gate. That is the hole the port above had just closed in one hop, reopened next to it, and `FareFreshness` already models the pattern. So `SyncDispatch` collects exactly `PollRoutePrices` and `RefreshRouteStats`, may not depend on `Infrastructure`, and is the only part of `app/Jobs` an Application class may name. `Queue` is the rest.

THE ARGUMENT AGAINST DOING IT THAT WAY, BECAUSE IT IS NOT A SILLY ONE. A layer whose definition is a list of two class names looks like a baseline wearing a hat, and this project forbids baselines absolutely. The distinction we are relying on is that a baseline enumerates *violations to ignore* while this enumerates *layer membership*: nothing is suppressed, the rule is stated in the positive, and a third job joining the list is a config edit that arrives in a diff under review rather than a suppression that arrives silently. If that distinction does not hold for you, the alternative is one line — put `- Queue` back under `Application` in place of `- SyncDispatch` — and its cost is the two-hop path above, which the gate would then call green. The stricter alternative is also one line, `Application: [Domain, Eloquent, Vendor]`, and its cost is the refactor: both jobs' bodies move into Application use cases and the jobs become wrappers.

TWO THINGS DEPTRAC CANNOT SEE FOR ITSELF, CLOSED IN `tests/Unit/Standards/LayerCoverageTest`. First, a whole new top-level directory is invisible: `app/Support/Helper.php` importing a facade and a controller gave `Violations 0, Uncovered 0` and exit 0, because a class in no layer has no rule to break. `--fail-on-uncovered` is on the step and catches the other direction — a dependency pointing *at* an unlayered class — but only `deptrac debug:unassigned` catches this one, so a test runs it and requires it to print nothing. Second, deptrac's default emitters see class tokens, not function calls: a Domain class calling `config()`, `now()` or `app()` is the framework arriving through a door it does not watch, and a `functionName` collector could not be made to fire on it. So the test tokenises every file under `app/Domain` and fails on any bare call to a function PHP does not ship — the same allowlist-of-internals trick the `Vendor` layer uses, rather than a blocklist of helper names that would rot the same way a namespace list would. Nothing in `app/Domain` calls one today; this keeps it that way.

NO BASELINE HERE EITHER. deptrac's `skip_violations` is a baseline by another name and is not used; there is nowhere for new debt to hide, the same standard `phpstan.neon` is held to. A wrong finding is a correction to the layers or the ruleset with the reason beside it in `deptrac.yaml`; a right one is fixed. The gate step runs `--no-cache`, and `.deptrac.cache` is gitignored for the local runs that do not — untracked, it is 1.9 MB the secrets step would copy out and scan, since `scripts/check.sh` lists the tree with `--others`.

### the-post-deploy-battery-does-not-write
`## Post-deploy verification` opened with "Everything below is a plain GET and safe to repeat", and a hundred lines further down, inside that same section, ran `-X PATCH -d '{"active":false}'` against `/api/watchlist/AMS-LIS` on production. The prose beside it said "pausing a route, then putting it back"; the putting-back command was in no version of this file. The header is what grants the permission — an operator or an agent reads it, treats the section as authorised-safe, works down it, and leaves a real watched route paused. Nothing then says so: the 06:10 poll skips an inactive route in silence, no alert fires for it, and the only trace is a toggle nobody is looking at. Found by the fleet deploy audit, 2026-08-31.

THE FIX IS A MOVE, NOT A DELETION. The CSRF trap the block existed to document is real and worth keeping — `SessionGuard::login()` regenerates the session, so a write signed with the pre-login token gets a 419 that reads exactly like a broken deploy. It now lives under `## Authenticated writes — not part of the battery`, outside the numbered list, headed by the warning that everything in it changes production data, and the pause and the restore are one block with the read that proves the restore landed. The battery above it is once again what its first line claims.

THE TEST BANS AN AUTHENTICATED WRITE, NOT A WRITE. `tests/Unit/Standards/DeployVerificationTest` joins the runbook's backslash-continued `curl` lines back into commands and fails on any one inside the verification section that carries `$AUTHED` and a write method. A blanket ban on `-X POST` would have been the obvious rule and the wrong one: the battery's cheapest auth check is a deliberate unauthenticated `POST /api/watchlist` asserted to come back `401`, which proves the CSRF token was accepted and can change nothing, because it never reaches the guard. What makes a command dangerous here is the session cookie, so that is what the test reads. A second test pairs the halves — a `"active":false` against a route code requires a `"active":true` against the same code somewhere in the file — because the missing restore, not the pause, is what turned this into an outage waiting for a reader.
